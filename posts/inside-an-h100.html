02 · Follow the work

A matrix multiplication, from outside in

Imagine two matrices, A and B, already waiting in device memory. We want C = A × B. Each entry in C is a sum of products. The mathematical instruction is short. Most of the engineering is in arranging where those values live and when they arrive.

  1. The application and its libraries arrange memory and launch a kernel. If the inputs start in host memory, they must first reach device memory. Subsequent operations can keep them there. Repeatedly copying the same data across PCIe can waste more time than the arithmetic takes.

  2. The kernel grid is divided into thread blocks. The device places blocks on SMs with enough resources. Threads form 32-thread warps. Registers, shared memory, thread limits, and block limits constrain how many can reside together. Occupancy is this residency, not a direct measurement of useful work.

  3. A large matrix is broken into tiles. Requests pass through the memory hierarchy; a cache hit can avoid a farther trip. Hopper kernels can use TMA to bring a tensor tile into shared memory asynchronously. Threads must observe completion before consuming it.

  4. Tensor instructions consume supported matrix tiles. Reusing a tile across many products increases useful operations per byte fetched from HBM. Hopper’s warpgroup matrix instructions let four warps—128 threads—cooperate on an asynchronous matrix operation. Layout and synchronization are part of the algorithm.

  5. While consumers compute, producers can prepare another buffer. Double buffering uses extra storage to overlap stages. The pipeline only works if dependencies are respected: data must be ready before it is read, and a buffer must be free before it is overwritten.

  6. Partial sums become output values. An epilogue may apply scaling, bias, or an activation before storing them. The next kernel may reuse the result from cache, read it from HBM, or communicate it to another GPU. The data does not have to return to the CPU after every operation.

Programming model: CUDA guide. A concrete implementation of the Hopper pipeline: NVIDIA’s TMA / WGMMA matrix example. This sequence is explanatory, not a trace captured from a running H100.

There is no single “GPU memory speed”

Registers hold a thread’s working values. Shared memory lets a block cooperate. L1 and L2 retain cached data. HBM holds the much larger working set. Each exists because keeping every value at the closest level would require too much silicon, power, or both.

At the smallest scale, transistors control electrical current. Circuits combine them into logic gates, storage cells, and larger arithmetic structures. A bit is a distinction maintained by a physical circuit; it is not a tiny written numeral. SRAM on the logic die and DRAM in the HBM stacks store that distinction differently. DRAM needs periodic refresh; SRAM uses more elaborate cells that retain state while powered.

Software can change how often it crosses those boundaries. Kernel fusion avoids materializing some intermediate results. Tiling reuses a small region many times. Better layouts make adjacent threads request adjacent data. More resident work can hide a wait, but cannot make a bandwidth limit disappear.

03 · Put the limits together

When does more arithmetic help?

Arithmetic intensity is the number of operations performed per byte transferred at a chosen memory boundary. Here the boundary is HBM. Multiply that intensity by memory bandwidth and you get a bandwidth-imposed ceiling. Compute imposes another ceiling. The lower one wins.

A simple HBM roofline

214.4 TFLOPSHBM bandwidth ceiling

min(989, 3.35 × 64) = 214.4 TFLOPS

The two ceilings meet near 295 FLOP/byte.

An ideal upper bound for a suitable kernel, not a benchmark. It assumes peak HBM bandwidth and the selected instruction’s peak rate, and omits latency, scheduling, cache effects, occupancy, communication, and power limits. Sparse throughput is intentionally excluded.

Roofline method: Nsight Compute profiling guide. Calculator values are our calculations from the product’s peak specifications.

Two examples make the difference visible

A BF16 vector addition: read two 2-byte values and write one 2-byte result. That is one floating-point addition for six bytes, or about 0.167 FLOP/byte. At 3.35 TB/s, the HBM ceiling is approximately 0.558 TFLOPS. This operation does not become a Tensor Core workload just because the chip has Tensor Cores.

A square BF16 matrix product: roughly 2N³ operations. In an idealized accounting where A and B are each read once and C is written once in BF16, HBM traffic is 6N² bytes. The intensity is N/3. At N = 4,096 that is approximately 1,365 FLOP/byte—above the dense BF16 balance point. Real tiling, rereads, output format, and other traffic change this accounting. FP32 accumulation can happen internally even when the final stored output is BF16.

The second example has an opportunity to spend much more time doing arithmetic on each fetched value. That opportunity is what a good kernel tries to realize.

Does the model fit?

Seven billion parameters stored at two bytes each occupy 14 GB before any other allocations. Seventy billion occupy 140 GB and cannot fit as BF16 weights alone in this GPU’s 80 GB. Quantization reduces that weight storage, but also introduces scale metadata and numerical tradeoffs.

Inference also needs activations, temporary buffers, and a key/value cache that grows with the active sequences and their lengths. Training adds gradients, optimizer state, and sometimes master weights. “The weights fit” and “the workload fits” are different claims.

As another deliberately optimistic calculation, streaming 14 GB once at 3.35 TB/s takes about 4.18 milliseconds. That is only a lower bound for that memory movement under those assumptions. It is not a measured token latency. Real decoding includes KV-cache traffic, computation, launches, and other costs; batching changes how much work can reuse a weight read.

04 · Decide what a number means

The format is part of the machine

A smaller number format lets the hardware store and move more values with the same resources. It also changes what can be represented. This is a numerical bargain, not a free lossless compression step.

FormatWhat to understand
FP64Double precision for calculations that need its precision and range. Ordinary and Tensor matrix operations have different peaks.
FP32General single precision. Common in accumulation and operations that are not low-precision matrix products.
TF32A Tensor Core compute mode with reduced input significand precision and FP32-like exponent range. It is not a general three-byte storage format.
FP16 / BF16Both use 16 bits. FP16 allocates more bits to the fraction; BF16 has a wider exponent range. They are not numerically identical.
FP8 E4M3 / E5M2Eight bits including the sign. Four exponent and three fraction bits, or five and two. Scaling helps keep the relevant values representable.
INT8Integer representation. Quantized models require a mapping between integer values and the quantities those values approximate.

Formats and instructions: PTX reference; FP8 tradeoffs: Micikevicius et al.; scaling recipes: Transformer Engine documentation.

Structured sparsity is another bargain. Supported sparse matrix operations exploit a prescribed pattern, commonly two nonzero values per group of four along the required dimension, with metadata telling the hardware where they are. An arbitrary matrix containing some zeros does not automatically qualify.

That is why “3,958 TFLOPS” needs its accompanying words: FP8 Tensor Core throughput with sparsity. It is not dense BF16 throughput, general FP32 performance, or the speed of an end-to-end model. The format, accumulation behavior, sparsity pattern, and workload all belong beside the number.

05 · The chip has a world around it

One GPU is one level of the system

NVLink moves data between GPUs. NVSwitch connects those links in a server fabric. A network adapter and the wider network connect servers. These are distinct boundaries, with different costs and different roles. NVSwitch is not another part of the H100 die.

The headline bandwidths also use different conventions. HBM’s 3.35 TB/s is a memory-interface bandwidth, not independent read and write rates that can both be sustained at that value. NVLink’s 900 GB/s and PCIe’s approximately 128 GB/s add two directions. Use roughly 450 GB/s and 64 GB/s respectively when comparing a one-direction transfer ceiling.

Link conventions: Hopper tuning guide and architecture description. System topology: Fabric Manager guide.

Splitting a model across devices creates communication. Tensor parallelism exchanges partial results; pipeline parallelism passes activations; data-parallel training coordinates gradients. Adding GPUs helps only to the extent that more useful work outweighs the communication and coordination it introduces.

Sharing, trusting, and keeping it running

MIG divides a GPU into hardware-backed instances with assigned compute and memory-system resources. It is useful when a workload cannot use the full device. It is not seven copies of the full 80 GB GPU. The selected profile determines what each workload receives. MIG guide.

Confidential computing addresses a different question: whether an application’s data and execution can be protected in a supported trusted environment. Attestation, firmware, drivers, host configuration, and verification policy all matter. MIG isolation and a complete confidential-computing deployment are not interchangeable claims. H100 security architecture.

ECC and memory repair mechanisms address hardware reliability. Power management and cooling help keep operation within limits. Checkpointing and recovery address failures at the application level. None of these eliminates the need for the others. Memory error management.

How would you check this on a real machine?

First identify the exact GPU, its enabled configuration, MIG state, driver, and power limit. Then profile the workload. Nsight Systems can reveal gaps, transfers, and coordination in a timeline; Nsight Compute can inspect individual kernels, memory traffic, occupancy, and instruction utilization.

Ask a specific question: are we waiting for HBM, failing to reuse data, issuing too little work, running the wrong instruction path, or communicating between devices? A high GPU-utilization percentage alone cannot distinguish those explanations. The atlas gives names to the places worth investigating; measurement tells you which one is limiting a particular job. Profiling guide.

Package and support

The green board is a carrier. It routes power and high-speed signals between the GPU package, voltage regulators, and the server’s baseboard. Baseboard connectionsPower and signals leave the module here

The module mates with a server baseboard. Its contacts carry power and communication signals, including paths used by PCIe and NVLink. The baseboard then connects the accelerator to the rest of the machine. An SXM module is not plugged into a desktop’s PCIe expansion slot.

DGX H100 system guide

Voltage regulatorsConvert supply power into local rails

The GPU needs tightly controlled voltages while its current demand changes rapidly. Switching regulators, inductors, and control circuitry convert the incoming supply into the rails used by the silicon. Their conversion losses become heat too. Supplying enough average watts is insufficient if voltage droops during a sudden burst of work.

The regulators feed the package through conductive planes and many connections; nearby capacitors help with faster changes.

Model note. The blocks represent regulator stages collectively. Rail voltages, phase counts, and the exact H100 module bill of materials are not modeled.

DGX H100 system guide

Decoupling capacitorsA nearby reserve of charge

A capacitor stores charge. Placed close to a load, it can supply brief current changes before a more distant power source responds. Many capacitors and the wiring between them form a power distribution network with frequency-dependent behavior. The goal is to keep supply voltage within limits as switching activity changes.

Capacitors, package connections, and voltage regulators work together. None performs the matrix multiplication, but the arithmetic depends on a stable supply.

Package substrateFan out dense connections

The package substrate sits between the fine wiring near the chips and the larger connections to the module. It provides mechanical support and routes signals and power across multiple layers. “The chip” in a product photograph often includes this package, not just the bare GPU die.

The interposer handles especially dense connections between adjacent dies; the substrate carries those connections toward the board.

TSMC CoWoS packaging

Silicon interposerShort, wide paths to HBM

An interposer lets the logic die and stacked memory sit side by side with very dense wiring between them. This is the central idea of a 2.5D assembly: several dies share an interconnect platform instead of talking only through long board traces. Short connections make a very wide memory interface practical.

HBM is close to the GPU, but it remains separate DRAM. The interposer is a connection layer, not an extra bank of GPU arithmetic units.

These solve different parts of the three-dimensional wiring problem: across an interface and through a die.

Hopper architecture

HBM3 memory stacks80 GB across five active stacks

HBM means high-bandwidth memory. DRAM dies are stacked vertically, then placed beside the GPU. A very wide interface allows many bits to move in parallel. This is where model weights, activations, and other large allocations usually live while the GPU works.

The five active stacks connect through ten 512-bit memory controllers: a 5,120-bit interface in total. HBM feeds caches and compute; it does not execute Tensor Core instructions.

Model note. This model shows five active stacks. The full GH100 design supports six; stack placement and the number of visible DRAM layers here are schematic.

Hopper architecture

Thermal interface and coolerUp to 700 W module TDP

Heat must leave the silicon through an interface material and a cooling assembly. Thermal interface material fills microscopic gaps; a heatsink or cold plate moves heat toward air or liquid. The server’s cooling system must then carry that heat away. A high power limit is only useful if temperatures remain controlled.

Clocks, voltage, workload, power limits, and temperature jointly affect sustained performance. A peak specification does not promise an indefinitely sustained operating point.

Model note. The removable finned assembly is a generic cooling illustration, not a specified H100 cooler. TDP is not a measurement of every workload’s draw.

H100 product specifications · DGX H100 system guide

DRAM dies inside HBMStacked storage, refreshed over time

A DRAM cell represents information using stored charge and an access transistor. Charge leaks, so DRAM needs refresh. HBM stacks many memory dies and connects them vertically. The stack exposes a wide interface to the GPU rather than behaving like a single long chain that every request must traverse.

On-chip caches use SRAM instead: storage circuits that retain state while powered without DRAM-style refresh. SRAM trades silicon area for access characteristics that suit nearby working data.

Model note. The four visible layers are an illustration, not the actual die count of an H100 HBM stack. Memory-cell circuits are explained, not individually modeled.

L2 cache50 MB shared on-chip cache

L2 is a cache between the SMs and off-chip memory. Reusing a value from L2 can avoid another trip to HBM. But fitting a tensor in HBM says nothing about fitting it in L2: these capacities differ by orders of magnitude.

An SM’s load can be satisfied nearer the computation if the data is already cached. Otherwise the request proceeds toward the memory controllers and HBM.

On-chip interconnectRoutes requests and responses

Compute units, caches, memory controllers, and external interfaces need a communication network inside the die. The interconnect routes their traffic. Moving a value has a cost in bandwidth, latency, and energy even when both endpoints are on the same chip.

MIG can assign distinct paths and cache resources to separate GPU instances. A full-size job and a partitioned job therefore see different available resources.

Memory controllers and PHYsTen active 512-bit controllers

Controllers turn memory requests into operations that the DRAM can perform. Physical interfaces, or PHYs, handle the electrical signaling. A wide interface helps throughput, but accesses still face scheduling, timing, and contention. Peak bandwidth is easier to approach with enough well-organized traffic.

Coalesced requests and reuse reduce unnecessary memory work. Random small reads are a different workload from a long contiguous transfer.

Hopper architecture · CUDA best practices

NVLink interfaces18 links · 900 GB/s bidirectional total

NVLink connects GPUs through a high-bandwidth fabric. The advertised aggregate adds both directions: 900 GB/s total corresponds to 450 GB/s in each direction across the links. It is not 900 GB/s of local HBM bandwidth, and it does not turn every other GPU’s memory into equally fast local memory.

NVSwitch can connect these links outside the GPU. Algorithms still need to partition work and communicate results.

Model note. Topology and software determine useful application bandwidth. NVSwitch is external and is not a block inside GH100.

PCIe host interfaceGen 5 ×16

PCIe provides a path to the host system and other devices. NVIDIA quotes roughly 128 GB/s with both directions added, or roughly 64 GB/s per direction. Protocol overhead and the actual system reduce useful payload throughput. The CPU typically launches work while the GPU executes kernels on data in device memory.

Loading a model from storage involves more than this link: storage, host memory, the driver, and allocation all participate.

Model note. An SXM H100 still has a PCIe interface. SXM is a form factor, not an alternative instruction set.

Hopper architecture

Copy enginesMove bytes while compute can proceed

Dedicated transfer engines support memory-copy work without spending the same arithmetic resources on every byte. Asynchronous copies can overlap computation when memory, streams, dependencies, and the hardware permit it. Merely using an asynchronous API is not proof that two operations overlap.

A host-to-device copy engine and the SM’s Tensor Memory Accelerator serve different scopes. TMA specializes in tensor transfers involving shared memory.

Model note. The illustrated block groups copy functionality; no engine count or precise physical placement is asserted.

CUDA programming guide · CUDA best practices

Work distributionFrom a kernel grid to resident blocks

A CUDA kernel launches a grid of thread blocks. The device schedules blocks onto SMs where resources are available. Blocks need registers, shared memory, and thread capacity; those demands constrain how much work can reside at once. Software does not generally assign each block a permanent numbered SM.

Once resident, the block’s warps are managed by SM scheduling machinery. Device-level dispatch and warp instruction scheduling are different stages.

Model note. This is a logical function, not a reverse-engineered map of the hardware dispatcher.

CUDA programming guide

Video and JPEG decodersSeven NVDEC · seven JPEG engines

Decoding compressed video and images is a different operation from multiplying matrices. Dedicated decode engines can help feed visual workloads without asking the general arithmetic lanes to perform every decoding step. They are relevant to an AI pipeline even when a language-only workload never uses them.

After decoding, data can still require preprocessing and transfer into the format consumed by a model.

Security and managementBoot, firmware, attestation

Confidential-computing support includes a chain of trust, protected execution paths, and evidence about the GPU’s security state. Attestation allows a verifier to check that evidence before trusting a workload with secrets. Firmware and management processors help establish and operate this environment.

Security depends on the host, driver, firmware, configuration, and verification policy as well as the GPU. Buying an H100 does not automatically make a running application confidential.

H100 confidential computing

Memory reliabilityECC and row remapping

Error-correcting codes detect or correct specified classes of memory errors. Row remapping can replace problematic memory rows with spare resources. Neither is a promise that every possible hardware or software fault will be corrected. Uncorrectable errors still need reporting and recovery.

Long training runs depend on reliability as well as speed. An incorrect value silently propagated through a calculation is a very different problem from a slow transfer.

Model note. Reliability mechanisms are distributed across the memory system. This tile is a conceptual callout, not one standalone ECC chip on the die.

GPU memory error management

Address translation and TLBsFrom virtual addresses to memory locations

Programs use virtual addresses. Memory-management machinery translates them using mappings maintained by the system. Translation lookaside buffers cache these mappings, so every load need not perform a full page-table walk. Missing in a translation cache is distinct from missing in a data cache.

A unified address space simplifies programming but does not make host memory and HBM identical in bandwidth or latency. Migration and remote access still involve physical movement.

Model note. This is a conceptual group. Page sizes, TLB structure, entry counts, and exact placement are not reconstructed here.

Clock and power managementTiming, limits, and operating state

Clock signals coordinate synchronous circuits. The device’s operating state affects how much work can be issued per second, while voltage and switching activity affect power. Management mechanisms monitor conditions and constrain operation when necessary.

A kernel can be limited by power or temperature before it reaches a published peak. A power cap is a limit, not an instruction to consume exactly that amount at every moment.

Inside and around an SM

Warp schedulersFour SM partitions

A warp contains 32 threads. A scheduler chooses an eligible warp instruction to issue; switching to other ready work helps hide waits. Dependencies, unavailable operands, barriers, and execution resources can all prevent a warp from issuing. Many resident warps are useful only if some have useful work ready.

Branches can make threads in a warp follow different paths. Inactive lanes do not perform useful work on a path they did not take.

Model note. A warp is a group of software threads, not 32 CPU cores. The four partition outlines are a schematic organization.

Hopper architecture whitepaper · CUDA programming guide

Register files65,536 × 32-bit registers per SM

Registers hold values used by executing threads: addresses, intermediate results, loop state, and accumulators. They are very close to the arithmetic, but finite. A kernel that needs more registers per thread can reduce the number of simultaneously resident warps.

If values spill, the compiler uses local memory. “Local” describes thread ownership; it does not guarantee that the storage sits in a register or even stays on chip.

Model note. The total register capacity is 256 KiB. Allocation granularity and other resources matter, so dividing capacity by thread count is only a first approximation.

Hopper tuning guide · CUDA best practices

FP32 arithmetic lanes128 per SM · 16,896 enabled on the GPU

These are the units counted as FP32 CUDA cores. They execute general single-precision floating-point arithmetic. A fused multiply-add computes a × b + c with one final rounding and is counted as two floating-point operations in throughput figures.

Elementwise operations, parts of normalization, and many non-matrix calculations need ordinary instructions. A Tensor Core peak is not the throughput of every instruction in a program.

Model note. A CUDA core is an arithmetic lane, not a fully independent CPU-style core with its own operating system thread.

Hopper architecture whitepaper · PTX instruction reference

FP64 arithmetic lanes64 per SM

Double precision uses 64-bit floating-point values and supports more precision than FP32. Many scientific calculations depend on this numerical behavior. H100 has dedicated FP64 arithmetic capacity as well as FP64 matrix operations on Tensor Cores.

Choose precision based on error tolerance and numerical stability. Smaller representations can improve throughput, but changing the representation can change the answer.

Model note. The FP64 Tensor Core peak and ordinary FP64 peak describe different operations; they are not interchangeable benchmarks.

Hopper architecture whitepaper

Integer arithmetic lanes64 per SM

Integer work includes addresses, indexing, counters, masks, and operations on integer data. It is part of the machinery of a matrix kernel even when the model’s values are floating point. The GPU must locate data and coordinate its work as well as calculate on that data.

Reducing address-generation overhead can matter when useful arithmetic is small or data movement is complex.

Model note. INT8 Tensor Core throughput does not describe INT32 lane throughput. The datatype and instruction both matter.

Hopper architecture whitepaper

Fourth-generation Tensor CoresFour per SM · 528 enabled in total

Tensor Cores execute matrix multiply-accumulate operations on supported tile shapes and numeric formats. Many scalar products are combined into one structured operation. The benefit comes when software lays out and supplies data so these units can keep working.

For C = A × B, each result is a sum of products. Inputs can use a smaller format while accumulation uses a wider one, depending on the instruction. Register and shared-memory layouts are part of making this work.

Model note. FP8, FP16, BF16, TF32, FP64, and INT8 have different capabilities and rates. There is no single meaningful “H100 FLOPS” number without the format and operation.

L1 / shared / texture storage256 KB combined capacity

L1 caches data automatically; shared memory is explicitly used by cooperating threads. On Hopper these functions draw from a combined on-chip storage resource. Allocating more shared memory changes the space available to caching. They are not two independent full-size pools.

A block can stage a tile in shared memory and reuse it repeatedly. That reuse can save much more time than simply increasing arithmetic throughput.

Model note. Up to 228 KB is available as shared memory per SM, with up to 227 KB per block. Larger dynamic allocations require the appropriate opt-in.

Hopper tuning guide

Load/store unitsConnect instructions to memory

Loads bring values into the execution path; stores write results out. The load/store machinery handles these instructions and their addresses. Nearby accesses by threads can be combined into fewer transactions, while scattered accesses can move many more bytes than the program actually uses.

Shared-memory accesses have their own bank structure. A pattern that looks parallel in source code may serialize when it creates bank conflicts.

Model note. The tile shows a functional group. The model is not a cycle-accurate memory simulator.

CUDA best practices

Special-function unitsSelected mathematical operations

Specialized instructions support operations such as approximate reciprocal and transcendental functions. A high-level function call may require several instructions, range handling, and corrections. Its cost and accuracy depend on the implementation and compiler options.

Exponentials in softmax are one reason a transformer is more than a sequence of matrix multiplications.

Model note. Do not assume every sine, exponential, or square-root call maps to one instruction or has the same precision behavior.

PTX instruction reference

Tensor Memory AcceleratorAsynchronous tensor transfers

TMA moves tensor-shaped regions between global and shared memory, and supports specified transfers within a thread-block cluster. One issuing thread can initiate work that would otherwise require many explicit address and copy instructions. The transfer proceeds while other work can continue.

Producer warps can prepare the next tile while consumer warps compute on the current one. A barrier establishes when the incoming data is safe to use.

Model note. TMA does not create extra HBM bandwidth. It reduces orchestration overhead and enables overlap when the pipeline has independent work.

Asynchronous barriersKnow when the data is ready

An asynchronous instruction returning does not necessarily mean its work has finished. Barriers and completion mechanisms coordinate producers, consumers, and accelerators. They prevent a computation from reading a tile before the transfer has completed or overwriting storage that is still in use.

The Hopper matrix example links TMA transfers, shared-memory buffers, and asynchronous matrix instructions into a pipeline.

Model note. This tile represents synchronization functionality. Correct ordering requires following the relevant instruction and memory-model rules.

DPX instructionsFused dynamic-programming operations

Dynamic programming builds solutions from related subproblems. Many recurrences repeatedly add values and choose minima or maxima. Hopper’s DPX instructions accelerate supported combinations of these operations, helping workloads such as sequence alignment.

An instruction specialized for a recurrence is a different form of acceleration from the matrix operations used by neural networks.

Thread-block clustersCooperation across SMs

A cluster groups thread blocks with a co-scheduling guarantee and mechanisms to cooperate across their SMs. Distributed shared memory lets a block access shared memory belonging to other blocks in its cluster. This can avoid some round trips through global memory.

The cluster is above an individual block in the programming hierarchy. It does not mean every SM can read every other SM’s shared memory at will.

Model note. This is a programming and execution relationship, not extra SRAM inside one SM. The portable maximum cluster size is eight blocks; H100 can opt into a nonportable larger size.

Transformer EngineHardware support plus software recipes

Transformer Engine combines supported low-precision arithmetic with software that manages scaling and format choices. FP8 cannot represent every value that FP16 or BF16 can. Scaling maps a tensor’s values into a useful range; the recipe must manage the loss of precision and overflow or underflow risk.

The E4M3 and E5M2 encodings trade significand precision against exponent range. Which tensors use which representation is a numerical decision, not just a storage setting.

Model note. This is a cross-cutting feature, not a separate processor hiding next to the Tensor Cores. Later Transformer Engine features are not all supported by Hopper.

Instruction fetch and cachesKeep the program near the execution units

The GPU needs instructions as well as data. Instruction caches retain the encoded program close to the SM’s execution machinery. Fetch and issue are separate from reading the matrix operands. Code size, instruction dependencies, and instruction mix can matter even when the data fits in cache.

The compiler turns source into executable instructions. A compact high-level expression can expand into many operations; a library call can launch several specialized kernels.

Model note. The label groups the instruction path. Cache capacity and detailed front-end geometry are not asserted.

What this model can tell you

This is an educational, procedural 3D model of documented architecture and representative packaging. It is not a teardown, CAD model, simulator, die photograph, or transistor netlist. Dimensions, wire routes, board population, package layer thicknesses, cooler design, and most block positions are illustrative.

The package view shows five active memory stacks, not a claim about every physical die position. GPU view contains 66 TPC tiles representing 132 enabled SMs, arranged schematically across eight GPC regions. The SM view groups resources into four partitions. Transformer Engine, DPX, reliability, and cluster callouts describe features or distributed functions; they are not extra independent chips. Exploding a logical view separates concepts that do not physically detach.

We can understand the major functional systems from public documentation. We cannot honestly enumerate every transistor, firmware routine, PCB component, or unpublished circuit. The atlas makes that boundary visible instead of filling it with invented detail.
